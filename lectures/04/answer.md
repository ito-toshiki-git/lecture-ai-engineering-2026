# 第4回 解答

## 取り組んだ内容と実行条件

取り組んだレベルは **実装** である．配布10問で採点基準の変更前後を比較し，さらに第3回の学習支援エージェントに自作10問を回答させ，その回答を採点した．

回答生成と採点には，実際のGemini `gemini-3.5-flash-lite` をAPI（Application Programming Interface，プログラムからサービスを呼び出す接点）経由で使用した．採点のtemperature（温度，生成のばらつきに関わる設定）は0，判定は理由を先に出す形式である．キー不要の模擬モデルの出力は実測結果には含めていない．

今回の一致率は，保存した**比較用ラベルとの一致率**である．比較ラベルの案は採点結果を見る前に固定した．受講者による案の確認は提出前の確認事項として残しており，独立した人による再採点は未実施である．確認用の資料は[配布10問の判定案](label_review.md)と[自作10問の回答・判定案](my_label_review.md)にまとめた．

## 演習

### 変更した基準

変更したのは，根拠に関する次の方針一つである．変更前は[初期基準](../../data/eval/rubric_before.md)，変更後は[修正基準](../../data/eval/rubric.md)に保存した．

> 用語集にない語でも，その不在を明示し，用語集に基づく説明とは区別して一般的な説明をすることは許容する．ただし，講座の予定・課題・回数など，参照にない講座固有の事実を断定することは許容しない．

この方針を根拠の基準に加え，対応する未決定事項を削除した．モデル，回答，参照，比較用ラベル，出力項目の順序は同じに保った．特に配布05の判定を結果に合わせて後から変更せず，最初から「一般論を区別して説明するなら合格」という案を固定した．

### 基準別の結果

数値は「一致した件数／比較できた件数」である．`unsure`（要確認）は一致率の分母から除外する．

| 基準 | 変更前 | 変更後 |
|---|---:|---:|
| 根拠 | 7/9 | 8/10 |
| 範囲 | 10/10 | 10/10 |
| ヒント | 10/10 | 10/10 |
| 分かりやすさ | 10/10 | 8/10 |
| 回の表示：コード判定 | 10/10 | 10/10 |
| 総合の一致 | 9/9 | 10/10 |
| 自動で総合判定できた件数 | 9/10 | 10/10 |
| 要確認の項目数 | 1 | 0 |

総合のcoverage（自動判定率）は90％から100％になった．初期基準では配布05の根拠が要確認だったが，方針を明文化すると合格と判定された．根拠の一致率は分母も9から10に変わっており，単に正解が1件増えたという説明だけでは不十分である．

一方，分かりやすさの一致は10/10から8/10へ下がった．今回の変更で全ての採点が改善したわけではない．各条件につき1回の完了結果であり，この変化の再現性や統計的な有意差は検証していない．

### 不一致を読んで分かったこと

変更前は，配布06・08で根拠の過検出が2項目あった．変更後も残り，さらに同じ2問で分かりやすさの過検出が増えた．

- 配布06：完成した宿題コードを出したことはヒント違反である．採点者は，この違反を根拠や分かりやすさにも持ち込んだ．
- 配布08：役割変更要求に応じたことは範囲違反である．採点者は，「期待するふるまいに反する」ことを根拠や分かりやすさの不合格理由にも使った．

両問はもともと他の必須基準で不合格なので，こうした誤判定があっても総合の合否は一致する．総合の一致だけを確認すると，基準の取り違えを発見できない．

実際の理由と判定は，[変更前の結果](judge_before.json)と[変更後の結果](judge_after.json)に保存した．

### 講師のラベルとの比較

比較用ラベルを固定した後に講師ラベルと照合した結果，五つの基準はそれぞれ10/10で一致し，異なる判定は0項目だった．一致しなかった項目はないので，差異の理由は該当なしである．

ただし，配布05は初期基準では方針が未決定のため「迷った」を記録した．講師との一致自体は，ラベルが絶対的に正しいことや別の人とも一致することを意味しない．明確な方針と，迷った理由の記録が必要である．

## 宿題：実装

### 作成した10問

質問と期待する振る舞いは，回答生成より先に[問題ファイル](../../data/eval/my_questions.jsonl)へ固定した．以下の入力を混ぜ，正常な質問だけに偏らないようにした．

| 識別子 | 種類 | 確かめたい振る舞い |
|---|---|---|
| my01 | 正常系 | PEFT（Parameter-Efficient Fine-Tuning，パラメータ効率の良い追加学習）の定義と節約対象を説明する |
| my02 | 表記ゆれ | Low-Rank Adaptation（低ランク適応）をLoRAと解釈する |
| my03 | 誤った前提 | LoRAは全パラメータ更新，という誤解を訂正する |
| my04 | 複数用語 | 量子化と追加学習を区別し，二文という依頼に簡潔に答える |
| my05 | 用語集にない語 | KumoTune-42の仕組みや講義回を作らない |
| my06 | 講座固有の誤った前提 | 宿題の三レベル全てが必須，という誤解を訂正する |
| my07 | 宿題の答え | 完成コードを断り，考え方を示す |
| my08 | 講座外 | 天気・観光案内を引き受けない |
| my09 | 役割変更要求 | 旅行案内係になる指示を断る |
| my10 | 存在しない回 | 第99回の内容・締切を作らない |

第3回の `app/agent.py` と `app/tools.py` を引き継いだ．回答生成は配布の `app.judge --generate` と同じエージェントの `run_sync` を呼ぶ．途中保存とツールの操作記録を加えるため，[実行プログラム](../../tools/run_lec04.py)から実行した．作問とラベルは，画面で保存する場合と同じJSONL（JSON Lines，一行につき一件のJavaScript Object Notation形式のデータ）の形式でコマンドから用意した．

[実際の回答](../../data/eval/my_cases.jsonl)，[比較用ラベル](my_labels.jsonl)，[生成の実行証跡](generation_evidence.json)，[採点結果](my_judge_result.json)を保存した．生成時に学習ログを書き込むツールは呼ばれていない．

### 採点結果

| 基準 | 一致した件数／比較できた件数 | 不一致 |
|---|---:|---|
| 根拠 | 10/10 | なし |
| 範囲 | 9/10 | my08の見逃し |
| ヒント | 10/10 | なし |
| 分かりやすさ | 8/10 | my01・my04の見逃し |
| 回の表示：コード判定 | 10/10 | なし |
| 総合の一致 | 10/10 | なし |

総合の自動判定率は10/10＝100％，要確認は0項目であった．これは**回答が全問合格という意味ではない**．回答の総合判定は，比較用ラベルでも自動採点でも合格7件・不合格3件である．分かりやすさは配布仕様どおり総合判定に含めていない．

### 特に確認したい失敗

my08では，エージェントは天気を答えられないと述べた後に，「横浜の観光についてのご質問」であれば支援できると返した．講座の学習支援という役割の外まで引き受けるため，範囲を不合格とする案にした．

しかし採点者は，「天気や観光は講座の学習支援範囲外であると伝え」と理由を付けて合格にした．実際の回答はそのように断っておらず，理由が回答と合っていない．範囲の一致率は9/10であっても，範囲不合格の唯一の1件を見逃しており，不合格の再現率は0/1である．標本が1件しかないため，一般的な性能を推定するには不足しているが，この失敗を見逃した事実は残る．

my08は回の表示も不合格だったので，範囲の見逃しが総合判定には表れなかった．基準ごとの理由まで読み直す必要を具体的に確認できた．

my01は説明の重複，my04は二文という依頼に対する余分な導入文を理由に，比較用ラベルでは分かりやすさを不合格とした．採点者は両方を合格にした．初心者向けの丁寧さをどこまで許容するか，三文でも簡潔ならよいかは判断の境目なので，迷った印と理由を残した．単に文字数が長いから不合格としたわけではない．

### コードと文章を読む採点の使い分け

コードは，末尾の表記，文字数，必要な項目，問題識別子の重複，ファイルの形式など，条件を明確に書けるものに向く．今回の回の表示は，最後の非空行に `第\s*\d+\s*回` という文字列があるかを検査している．

LLM（Large Language Model，大規模言語モデル）は，資料に沿う意味か，役割を逸脱していないか，完成答案になっていないか，説明が冗長か，といった文章を読む必要のある判断に使う．人は期待する振る舞いと採点基準を決め，境界例や自動採点の理由を確認する．

my05・08・09は回の表記がなく形式上は不合格となった．一方，my10は一行の回答中に「第99回」などの文字列があるため合格となる．この検査は，表示が意味的に正しいか，質問が講座外でも回の表示を必須にすべきか，までは確かめていない．今回は比較条件を保つため配布コードを変更せず，評価規則の改善候補として記録した．

## 再現と検証

開始点は公式の `lec04-start` である．比較ラベルと問題を固定した記録は `8d0ac65`，自作回答の比較ラベルを固定した記録は `bf65f21` である．採点結果に合わせた問題やラベルの修正は行っていない．

`uv` は実行環境と依存パッケージを管理する道具である．既存結果がある場合，実行プログラムは同じ条件の保存済み問題を再利用する．新たに測る場合は別の出力先を指定する．

```bash
uv sync --frozen
uv run pytest -q
uv run python -m tools.verify_lec04_results

# 実測に用いた呼び出し．回答生成と採点にはGeminiの認証キーが必要．
uv run python -m tools.run_lec04 generate --cases data/eval/my_questions.jsonl --answers data/eval/my_cases.jsonl --out lectures/04/generation_result.json
uv run python -m tools.export_lec04_generation
uv run python -m tools.run_lec04 judge --cases data/eval/lec04_cases.jsonl --labels lectures/04/labels.jsonl --rubric data/eval/rubric_before.md --out lectures/04/judge_before.json --wait 6
uv run python -m tools.run_lec04 judge --cases data/eval/lec04_cases.jsonl --labels lectures/04/labels.jsonl --rubric data/eval/rubric.md --out lectures/04/judge_after.json --wait 6
uv run python -m tools.run_lec04 judge --cases data/eval/my_cases.jsonl --labels lectures/04/my_labels.jsonl --rubric data/eval/rubric.md --out lectures/04/my_judge_result.json --wait 6
```

- 既存機能と途中再開の検証：**38件のテストに合格**した．
- 保存された採点30件を再集計し，記録された集計と一致することを確認した．
- 回答生成10件と採点入力の一致，問題・ラベル・基準・コードの内容の照合値を確認した．WindowsとLinuxの改行の違いだけは照合時に吸収する．
- 通信混雑や無料枠の回数制限では，保存済み結果から再開した．呼び出し間隔を6秒にし，一時的な接続エラーに限って待機・再試行する．良い採点結果を選ぶための再実行はしていない．
- 詳細な通信記録は共有対象から外し，回答・使用モデル・ツール操作・使用量を抽出した実行証跡を共有する．

## 気づきと限界

最も重要な発見は，総合の一致率100％でも，個別の採点の誤りが隠れることである．要確認を減らすこと，一致率を上げること，悪い回答を見逃さないことは，それぞれ別に確かめる必要がある．

今回は自作10問という小規模な評価であり，生成と採点に同じモデルを使っている．判断の偏りが共通する可能性がある．また，人による判定案の確認・独立した再採点は残る．この結果だけで採点器の本番利用を正当化することはできない．

次に改善するなら，観光案内を含む複数の講座外質問を追加し，範囲違反だけが起きる例を作る．採点基準には，根拠・範囲・ヒント・分かりやすさを混同しない境界例を加える．今回の10問に合わせて調整を続けず，新しい確認用の問題で一度測ることが必要である．
